# Design Core Harness (시각 검증 공통 하네스)

디자인 작업이 코드만으로 완료될 수 없음을 전제하는 **공통 실행 프레임**.
이 스킬은 도메인별 미학 지식이 아니라, **"어떻게 하면 렌더링 결과를
실제로 보고, 결함을 찾고, 다시 고칠 것인가"**의 절차와 판정 기준을
소유한다.

> 이 스킬은 `frontend-design`(통합 미학 프레임워크)과 **역할이 다르다.**
> frontend-design이 "무엇이 좋은 디자인인가"의 라이브러리라면, 본 스킬은
> "그 디자인이 실제 화면에서 완성되었는가"의 **검증 하네스**다.
> 구현 전 계약(design.md)과 구현 후 검증(Visual QA Loop)이 본 스킬의
> 두 축이다.

---

## 1. 핵심 철학 (MiMo Design Philosophy)

디자인 산출물을 다룰 때는 아래 두 명제가 모든 작업의 전제가 된다.

> **"렌더링 전까지 완성 아님 (Not done until rendered)."**
> 코드가 논리적으로 옳아 보여도, 실제 화면에서 깨졌다면 그 작업은
> 완료가 아니다. 코드만 보고 "완성"을 선언하는 것은 금지된다.

> **"No console errors is the floor, not the finish line."**
> 콘솔 에러가 없다는 것은 시작점일 뿐 완성 기준이 아니다. 에러 없는
> 화면도 시각적으로는 결함투성이일 수 있다. 시각 대조(Vision Diff)를
> 통과해야만 완료다.

### 1.1 파생 원칙

1. **1차 산출물은 렌더링 가능한 단일 파일**, 검증 루프를 돌릴 수 없는
   산출물은 1차 완료로 인정하지 않는다. (앱 통합 코드는 code 모드 인계)
2. **자기 판정 금지**, 코드 작성자가 "아마 괜찮을 것"으로 판정하지
   않는다. 반드시 화면을 띄우고 눈(또는 도구)으로 확인한다.
3. **수정은 1결함 단위**, 여러 결함을 한 번에 고치려다 원인을 잃지
   않는다. 하나 발견 → 하나 수정 → 재렌더링.

## 2. 시각 검증 루프 (Visual QA Loop)

모든 시각 산출물은 아래 4단계 루프를 **1회 이상** 통과해야 한다.

```text
① 렌더링(Render) ──▶ ② Vision 대조(Inspect) ──▶ ③ 수정(Fix)
        ▲                                              │
        └──────────────── ④ 재렌더링(Re-render) ◀──────┘
```

### 2.1 단계별 절차

| 단계 | 액션 | 규칙 |
|------|------|------|
| ① 렌더링 | 산출물을 실제 화면으로 렌더링한다 | 도구 우선순위는 §7 폴백 체계를 따른다. 정적 코드 열람은 렌더링이 아니다 |
| ② Vision 대조 | 스크린샷을 Vision 능력으로 검사한다 | §3 4대 결함 체크리스트 + §4 슬롭 블랙리스트를 대조한다. 명세(design.md)와 diff한다 |
| ③ 수정 | 발견된 결함을 수정한다 | 1결함 단위. 원인을 한 문장으로 서술한 뒤 수정한다 |
| ④ 재렌더링 | 수정본을 다시 렌더링한다 | 결함이 0이 될 때까지 ①~④를 반복한다. 반복 횟수에 상한을 두지 않는다 |

### 2.2 루프 완료 판정 조건

아래 3가지가 **모두** 충족될 때만 루프를 종료하고 완료를 선언한다.

- [ ] 4대 시각 결함(§3) 중 어느 것도 발견되지 않음
- [ ] 슬롭 블랙리스트(§4)에 하나도 매치되지 않음
- [ ] design.md 사전 계약(§6)의 선언값과 실제 렌더링이 일치함
      (컬러 hex, 타이포 크기, 다이얼 값 범위)

## 3. 4대 시각 결함 체크리스트

Vision 대조 시 **반드시** 아래 4가지를 의심하고 확인한다. 렌더링 결과를
볼 때 이 4가지를 "대충 봤다"로 넘기면 안 된다.

### 3.1 텍스트 디센더/어센더 잘림 (Ascender/Descender Clipping)

- **증상**: `g`, `j`, `p`, `q`, `y`(디센더) 또는 `b`, `d`, `h`, `k`,
  `l`, `t`(어센더)의 끝이 부모 박스·오버플로 숨김에 잘려 보인다.
  한글의 경우 `ㅇ`, `ㅎ` 받침과 괄호 `( )` 상하 여백이 눌려 보인다.
- **의심 지점**: 고정 높이 박스(`height`, `line-height` 고정) 안의
  텍스트, `overflow: hidden` + `padding` 미지정 조합, `line-height: 1`
  미만 설정.
- **판정**: 어센더/디센더 글자가 들어간 실제 문구로 렌더링해 육안 확인.
  테스트 문구 예: `"행복한 팬더 LazyTy pjq"` → `L`, `y`, `p`, `j`, `q`
  모두 온전해야 한다.

### 3.2 z-index 충돌 및 레이아웃 겹침 (Overlap)

- **증상**: 모달·드롭다운·스티키 헤더가 다른 요소에 가려지거나,
  두 요소가 반쯤 포개져 텍스트가 서로 겹쳐 읽히지 않는다.
- **의심 지점**: `z-index` 미지정 스태킹 컨텍스트, `position: absolute`
  좌표가 부모 기준이 아닐 때, `transform` 생성 스태킹 컨텍스트.
- **판정**: 겹침이 의심되는 영역을 확대해 위/아래 요소의 경계를 확인.
  시각적으로 모호하면 요소별 `outline`을 임시 켜서(검증 후 제거)
  경계를 확인한다.

### 3.3 플레이스홀더 텍스트 잔존 (Placeholder Text)

- **증상**: 구현 의도와 무관한 미치환 자리표시자 텍스트가 화면에 남는다.
- **단골 패턴**: `"Lorem ipsum"`, `"Title"`, `"Your Title Here"`,
  `"Description"`, `"Content goes here"`, `"TODO"`, `"Sample"`.
- **판정**: 렌더링 화면 전체에서 위 단골 패턴을 문자열 검색 + 시각 확인.
  발견 즉시 실제 콘텐츠로 교체한다. **하나라도 남으면 루프 불통과.**

### 3.4 전경-배경 명도 대비 미달 (Figure-Ground Contrast)

- **증상**: 텍스트가 배경과 명도 차이가 부족해 읽기 어렵다. 특히
  컬러 배경 위 동일 계열 텍스트, 그라디언트 위 흰 텍스트, 50% 이하
  불투명 텍스트.
- **판정 기준**: 일반 텍스트 **4.5:1 이상**, 대형 텍스트(24px/19px bold
  이상) **3:1 이상**, WCAG AAA를 요구하는 산출물(SVG 조판 등)은
  **7:1 이상**.
- **의심 지점**: §4 블랙리스트의 `cyan-on-dark hero`처럼 채도 높은
  배경 위 저대비 텍스트.

## 4. 슬롭 블랙리스트 (Slop Blacklist)

아래 5개 패턴 중 **하나라도** 렌더링에 매치되면 즉시 반려(Reject)하고
수정으로 돌아간다. 이는 AI 디자인의 "밋밋함/제너릭함"이 실제로 화면에
구현된 형태들이며, 사용자 최대 불만의 직접 원인이다.

| # | 블랙리스트 패턴 | 판정 기준 |
|---|----------------|-----------|
| 1 | **보라-파랑 그라디언트 남용** | 히어로/버튼/배경에 `#6366f1→#8b5cf6`, `#3b82f6→#a855f7` 류의 남색↔보라 그라디언트가 기본 장식으로 깔려 있음 |
| 2 | **균일 3열 카드 그리드** | 같은 크기·같은 간격 카드 3개가 반복되며 시각적 위계·비대칭 없음 (VARIANCE ≤ 3에서만 허용) |
| 3 | **기본 폰트 스택 (Inter on gray)** | 시스템 기본(Inter/맑은 고딕) + 회색 배경(#f9fafb 류)만으로 구성, 시그니처 타이포·컬러 의도 없음 |
| 4 | **반복적 박스+그림자** | 모든 콘텐츠가 흰 카드(`border-radius`+미세 그림자)로 감싸인 "박스 위 박스" 레이아웃 |
| 5 | **cyan-on-dark hero** | 어두운 배경에 시안(#06b6d4/#22d3ee) 포인트+흰 텍스트의 클리셰 히어로 |

> **반려 후 행동**: 어떤 항목이 매치됐는지 한 줄로 기록하고, §5 안티-
> 제너릭 3중 방어선의 해당 단계(다이얼 재선언/시그니처 강화/대체안)로
> 되돌아간다. "그럴듯하니까 넘어가기"는 금지.

## 5. 안티-제너릭 3중 방어선 (Anti-Generic Triple Defense)

제너릭 디자인이 산출물에 스며드는 것을 **구현 전·중·후** 3단계로 차단한다.
어느 한 단계라도 통과하지 못하면 다음 구현으로 진행할 수 없다.

### 방어선 ① design.md 다이얼 필수 선언 (구현 전)

구현을 시작하기 **전에** `design.md`(§6 프로토콜)에
VARIANCE / MOTION / DENSITY 3개 다이얼 값을 반드시 선언한다.
값 없이 구현을 시작하면 설계 의도가 없는 상태이므로 즉시 중단한다.

- 다이얼 의미·범위는 [`frontend-design`](../frontend-design/SKILL.md)의
  §2 (The Three Dials)를 따른다.
- 선언 예: `DESIGN_VARIANCE: 6 / MOTION_INTENSITY: 3 / VISUAL_DENSITY: 4`

### 방어선 ② 시그니처 요소 1개 이상 필수 (구현 중)

화면 어디에나 하나는 "이 디자인이 다른 어디에도 없다"고 말해주는
**시그니처 요소(Signature Element)** 를 반드시 포함한다. 시그니처 후보:

- 비대칭 그리드 / 오프그리드 정렬 (VARIANCE ≥ 5일 때)
- 특이한 타이포 조합(대비 폰트 페어링, 대문자 라벨+리딩 조절)
- 독특한 경계 처리(이중 보더, 점선 앵커, 라운드-스퀘어 혼합)
- 고유한 모션 언어(커스텀 이징, 스크롤 리빌 시퀀스)
- 장인적 디테일(커스텀 커서, 마이크로인터랙션, 특이한 콘텐츠 리듬)

> "시그니처 없음" = 제너릭. 방어선 ②를 통과하지 못하면 ①로 돌아가
> 다이얼을 올리고 다시 설계한다.

### 방어선 ③ 블랙리스트 시각 대조 (구현 후)

렌더링 완료 후 §4 슬롭 블랙리스트 5개 항목을 **스크린샷에 직접 대조**
한다. 하나라도 매치되면 반려 → 수정 → 재렌더링.

```text
[① 다이얼 선언] ──▶ [② 시그니처 포함] ──▶ [③ 블랙리스트 대조] ──▶ 통과
     ▲                    ▲                        │매치
     └────────────────────┴────────────────────────┘
```

## 6. design.md 사전 계약 프로토콜 (Pre-Contract)

시각 산출물 작업 시 **구현 전에** `design.md` 계약서를 작성한다.
이 계약서는 (a) 구현의 설계 기준이 되고 (b) 검증 루프의 대조 명세가 된다.

### 6.1 필수 선언 항목

```markdown
# design.md (사전 계약)

## 1. 목적
[이 화면/산출물이 전달할 단 하나의 핵심 메시지]

## 2. 다이얼 선언 (frontend-design 체계)
- DESIGN_VARIANCE: [1-10], 근거 한 줄
- MOTION_INTENSITY: [1-10], 근거 한 줄
- VISUAL_DENSITY: [1-10], 근거 한 줄

## 3. 컬러 계약
- Primary: #HEX (용도: ...)
- Surface/배경: #HEX
- 텍스트(전경): #HEX, 배경 대비 비율 명시 (예: 12.4:1)
- 포인트/강조: #HEX

## 4. 타이포 계약
- 본문: [폰트], [size]/[line-height]
- 헤딩: [폰트], [size]/[line-height]
- 라벨/대문자: [size], letter-spacing
- 한글/라틴 폴백 규칙

## 5. 모션 계약
- 전환/이징: [duration, easing]
- 인터랙션 상태별 동작

## 6. 레이아웃 계약
- 그리드/여백 시스템, 시그니처 요소 명시
```

### 6.2 계약서 규칙

1. 컬러·타이포·모션·레이아웃·다이얼 **5종 모두** 구현 전 명문화한다.
2. 검증 루프 ② 단계에서 이 계약서와 실제 렌더링을 diff한다.
3. 계약 위반이 발견되면 (a) 계약 수정 또는 (b) 구현 수정 중 하나를
   선택해 **한쪽을 반드시 정합**시킨다. 방치 금지.

## 7. 시각 검증 도구 폴백 체계 (Tool Fallback Ladder)

렌더링 수단은 아래 순서로 시도하고, 사용 가능한 도구가 없을 경우
"시각 미검증" 상태로 강등한다. **도구가 없다고 검증을 건너뛰면 안 된다.**

```text
1순위: scripts/visual_qa.js  (Playwright 헤드리스 전체 페이지 스크린샷)
   │  node scripts/visual_qa.js <html_path> [out_dir] [--flow flow.json]
   │  ※ Node Playwright 미설치 시 같은 폴드의 visual_qa.py
   │    (Python Playwright)로 자동 폰백
   ▼
2순위: view_file (헤드리스 스크린샷 읽기 폰백)
   │  1순위가 남긴 PNG를 view_file로 읽어 Vision 대조한다.
   │  사용자 화면에 창을 띄우는 캡처는 금지(AGENTS.md §10)
   ▼
3순위: 순수 명세 강등 (Spec-only Downgrade)
      코드·명세 대조만 수행 + 산출물에 "시각 미검증(UNVERIFIED)" 배지 부착
```

### 7.1 1순위, visual_qa.js (권장)

- 스크립트 경로: `scripts/visual_qa.js` (본 스킬 디렉토리)
- 사용법: `node visual_qa.js <html_path> [out_dir] [--flow flow.json]`
- Playwright를 **peer 의존성**으로 간주(동적 import). Node Playwright
  미설치 시 같은 폴드의 `visual_qa.py`(Python Playwright)로 **자동
  폰백**하므로 둘 중 하나만 있으면 된다.
- 클릭·입력·스크롤 흐름 검증은 `--flow <flow.json>`으로 수행한다.
  헤드리스로 단계별 조작 + 단계별 스크린샷을 남기므로, 사람이 마우스로
  클릭하는 테스트를 인라인으로 대체한다. 스키마는
  [`scripts/visual_qa.py`](scripts/visual_qa.py) 주석 참조.
- 상세 사양은 [`scripts/visual_qa.js`](scripts/visual_qa.js) 참조.

### 7.2 2순위, view_file 폰백

`visual_qa.js`를 쓸 수 없으면 1순위가 남긴 **헤드리스 스크린샷 PNG**를
**view_file**로 읽어 Vision 대조한다. agy-pro의 view_file / 시각 검증 도구은
이미지 파일을 에이전트가 직접 보는 네이티브 도구이므로 별도 MCP 설치가
필요 없다. 사용자 화면에 창을 띄워 캡처하는 방식은 **금지**(AGENTS.md
§10); 헤드리스 캡처가 전무하면 3순위로 강등한다. 이 경우 산출물이
화면 전체가 아닐 수 있으므로 "부분 검증"임을 결과에 명기한다.

### 7.3 3순위, 순수 명세 강등 + 배지 (UNVERIFIED)

렌더링 도구(Playwright·view_file)가 **모두** 불가능한 환경이면:

1. 코드와 design.md 명세 간 논리 대조(좌표·컬러 hex·타이포 값)만 수행한다.
2. 산출물 결과에 아래 배지를 **반드시** 부착한다. 배지 없이 완료
   선언하는 것은 금지된다.

```text
⚠️ 시각 미검증(UNVERIFIED), 렌더링 도구 없이 명세 대조만 수행됨.
실제 화면 검증(Visual QA Loop) 전에는 이 산출물을 완성으로 간주하지
말 것.
```

## 8. 후속 스킬 연쇄 로드 규칙 (Chained Loading)

웹 UI/시각 산출물 작업 시 본 하네스(절차·검증) 다음으로
**`frontend-design`(통합 미학 프레임워크)** 를 연쇄 로드한다.
frontend-design 하나에 방향 다이얼·타이포·컬러·모션·카피 규칙이
통합되어 있다.

- 각 스킬 로드 시 해당 SKILL.md의 지침을 작업 컨텍스트에 반영한다.
- 본 스킬(design-core-harness)은 **항상 최초 로드** 후 frontend-design을
  이어 로드한다. (하네스가 절차, frontend-design이 미학 라이브러리)

## 9. 완료 선언 최종 체크리스트

어떤 시각 산출물이든 "완료"를 선언하기 전에 아래를 모두 통과했는지
확인한다.

- [ ] Visual QA Loop(§2)를 1회 이상 수행했고, 렌더링 수단이 무엇이었는지
      기록됨 (visual_qa.js / view_file / 명세 강등)
- [ ] 4대 시각 결함(§3) 0건
- [ ] 슬롭 블랙리스트(§4) 매치 0건
- [ ] design.md 계약서(§6)의 5종 선언과 렌더링 정합
- [ ] 시그니처 요소(§5 방어선②) 1개 이상 존재
- [ ] 명세 강등으로 검증한 경우 "시각 미검증(UNVERIFIED)" 배지 부착됨

> 검증 수단을 기록하지 않은 완료 선언, 그리고 도구 없이 배지 없이
> 내린 완료 선언은 **거짓 완료**로 간주한다.
